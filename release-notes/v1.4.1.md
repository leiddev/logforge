# logforge 1.4.1

The README learns to answer the question a reader arrives with, and four
comments stop describing a version of the library that no longer exists.

Nothing here changes the API, the behaviour or the build. A 1.4.0 consumer
needs no edits.

## Why this release

The library explained what it does -- one interface, a text record, a backend --
but not why it exists next to spdlog, which is the first thing somebody
choosing a logging layer asks. The pieces of the answer were scattered across a
bullet list, the target table and comments in a header, and one part of it was
not written down anywhere: a package built with the backend asks CMake for
spdlog even when the consumer links only `logforge::core`.

## What the README now says

Four sections, in the order the questions come up:

- **Why not spdlog directly.** What you get against what you give up: call
  sites that survive a backend swap, no spdlog or fmt header in a producer, a
  renderer that never throws -- against fmt's format language, the sinks and
  modes this library does not have, and the absence of a registry. It ends with
  when to keep spdlog, because a comparison that never says so is an
  advertisement.
- **Where spdlog is allowed to appear.** Headers, CMake targets, process state
  and package config, layer by layer. `install_as_default()` changing spdlog's
  global logger is a deliberate side effect, and the package config asking for
  spdlog unconditionally is the price of shipping the backend.
- **What the spdlog backend uses.** The whole API surface -- logger, the
  string-view dispatch overload, four sinks, the level enum, `source_loc`,
  `string_view_t`, the pattern language -- and what it does not use: async
  logging, periodic flush, the error handler, backtrace, the registry. That
  turns "write another backend" into an estimate.
- **Replacing the backend.** Four steps, the behaviour to reproduce, and the
  one thing a swap does not fix: a dependency that logs through spdlog's global
  logger does not move because logforge's backend moved.

## What else changed

- The first README bullet named `log(level, text, size)`, which is not the
  interface, and said the core "includes nothing", which reads as "no standard
  headers". Both now match the code.
- `docs/LOGGING.md` states two rules a backend author could previously violate
  in silence: `log()` is called from several threads, and `enabled()` must
  agree with what `log()` writes.
- `spdlog_backend.hpp` no longer promises a public surface without a spdlog
  type, which `native()` and `native_shared()` contradict. It says what the
  forward declaration buys instead.
- `examples/backend_configuration.cpp` uses `install_as_default()`, the path
  the documentation recommends, instead of installing and clearing the default
  by hand.
- Two `CMakeLists.txt` comments from milestones 0.4 and 1.0 are gone.

## What to do

Nothing. Read the README's *Replacing the backend* before you write a second
backend, and `LOGGING.md` section 7 before you implement one.
